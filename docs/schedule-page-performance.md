# Schedule page responsiveness and shared theme

The schedule bootstrap now releases the employee selector after `getSchedulePageData`. Owner user-scope administration loads separately with its own loading/error status, so it no longer blocks the selected employee's schedule. Bootstrap no longer requests the selected employee's policies a second time before `loadSelected` requests them. Refreshing policies explicitly ignores the browser click event rather than treating that event as a staff ID.

Concurrent identical, allowlisted reads share one pending transport promise. Different employees, dates and payloads remain separate. Settled successes and failures are removed immediately; there is no persistent cache. Every non-allowlisted action invalidates pending lookup entries before execution. Writes retain existing request IDs and are never combined or automatically retried. An older request's cleanup cannot delete a newer request's entry.

`getScheduleSelection` returns weekly rows, exceptions, resolved days and audit together, replacing four browser requests with one. With the transport's two-request concurrency limit, this removes three queued waves of schedule/policy reads. Policies remain a separate owner-only request. Each schedule section preserves its own success/error result, so an invalid date range does not erase a successfully loaded weekly schedule. Existing selection-sequence checks prevent superseded responses from replacing a newer selection. Weekly write actions no longer appear when no employee is selected, including during bootstrap.

The bundle first authenticates, requires `schedule.view`, and verifies access to the selected staff member. It then runs a fixed list of the four original read handlers with the server's actor and repository. Caller-supplied actor identities, child actions, staff-ID arrays and limits are ignored. Original read permissions, branch/employee scopes, 63-day range validation, 200-record limits and sensitive-field filtering remain in force. The bundle executes no mutations and does not change authentication/session policy.

The production scheduling repository now shares an isolated, request-local snapshot for server-allowlisted read actions. Audit permission filtering previously re-read the complete STAFF sheet for every audit row. The same filtering now uses one STAFF read per request; a fixture with 25 audit rows drops from 25 STAFF reads to one, with identical owner, employee and branch-manager responses. Returned nested objects and Dates are copied to protect the snapshot. Each new request reads again. Write/unknown actions and default repository construction retain live reads; locks, authorization, scope checks, conflict validation, calculations, compensation and persistence remain unchanged.

The page now uses the same SALONIX brand header, shared background/colors, white rounded panels, warm controls and brown/beige buttons as attendance and financial pages. All existing dialog/action IDs and hidden permission controls remain wired; tables scroll inside their panels. Styles load after the shared shell. `performance=1` logs only allowlisted action names and elapsed transport milliseconds, never staff payloads, tokens or records.

Validation: focused scheduling, scope/policy, rollback, copy, stale-selection and concurrent-read tests; read-only production checks. Real employee schedules are never changed for speed testing. Google Apps Script/Sheets request latency remains a constraint: this frontend change does not guarantee that every operation completes within six seconds.

Production observations on 2026-10-16: before bundling, weekly/range/overrides/audit reads finished at 6.533 / 12.435 / 12.439 / 18.214 seconds after selection, consistent with the two-request transport queue. After bundling, all four sections arrived together in 6.729 seconds; the parallel policies request took 6.704 seconds. Initial roster load took 4.805 seconds. These are individual live observations, not a six-second guarantee or a controlled benchmark. Weekly row text and the complete 14-day resolved range matched the pre-change live values exactly. The default 777px viewport had no page-level horizontal overflow.

Release verification: 1,387 tests passed; isolated deployment HTML, JS and CSS matched the tested files byte-for-byte. Backend read changes were published to Apps Script v69 without altering script properties or creating financial/employee test records.

A subsequent refresh completed the bundle in 5.880 seconds and policies in 5.873 seconds. Two immediate clicks produced one bundle transport and one policies transport, confirming in-flight deduplication on the live page. The copy dialog opened and closed without submission, page status cleared, and no console errors/warnings were captured. No claim is made about live write latency; copies and mutation compensation were tested with synthetic repositories only.
